## Known Bugs

### Search Only Filters by Book Name

- **Symptoms:** User cannot find a book by searching for author name, category, or price — the filter on line 97 only checks `book.name.toLowerCase().includes(searchText)`.
- **Files:** `script.js` (lines 96–98)
- **Trigger:** Type an author name like "James Clear" or a category like "Productivity" into the search bar — no results match.
- **Workaround:** Search only by the exact or partial book title.
- **Impact:** Major usability limitation — users expect search to cover all visible book fields (title, author, category).

### No Empty State When Search Returns Zero Results

- **Symptoms:** When the search text does not match any book, the grid goes completely blank with no message. User sees a white empty page area with no feedback.
- **Files:** `script.js` (line 83 — `displayBooks()` is called with an empty array, which renders an empty string)
- **Trigger:** Type a non-existent book name into the search bar.
- **Workaround:** None.
- **Impact:** Confusing UX — users may think the app is broken.

### External Image URL Dependencies With No Fallback

- **Symptoms:** 9 out of 18 books load cover images from external CDNs (OpenLibrary, Unsplash). If these services are slow, down, or the ISBN changes, broken image icons appear with no fallback styling or placeholder.
- **Files:** `script.js` (lines 30–47 — image URLs for books 1,2,3,8,9,12,13,14,15,16,17)
- **Trigger:** External CDN outage or URL change.
- **Workaround:** None — the `<img>` tag has no `onerror` handler and no CSS fallback beyond the gray `background-color: #E2E2E7` visible while loading.
- **Impact:** Visual degradation — books show broken image placeholders.

### Invalid HTML — `<div>` Children Inside `<ul>`

- **Symptoms:** Browsers may silently move `<div>` elements outside the `<ul>`, causing layout breakage.
- **Files:** `index.html` (line 16), `script.js` (line 83)
- **Trigger:** Rendering the book list.
- **Workaround:** None needed in most modern browsers (they auto-correct), but violates W3C spec.
- **Impact:** Potential layout or accessibility issues in strict rendering modes.

## Security Considerations

### `innerHTML` Used for DOM Rendering

- **Risk:** The `displayBooks()` function uses `booksList.innerHTML = finalHTML` (line 83) to render book cards. While the current data is hardcoded and safe, if the application is ever extended to load book data from an API or user input, this creates a stored XSS vulnerability — an attacker could inject `<script>` tags or event handlers through book names, author names, or image URLs.
- **Files:** `script.js` (line 83)
- **Current mitigation:** Data is entirely hardcoded — no dynamic or user-supplied content is rendered.
- **Recommendations:** Replace `innerHTML` with DOM API methods (`document.createElement`, `appendChild`, `textContent`) or use `insertAdjacentHTML` with sanitized data. If `innerHTML` must be kept, sanitize all string values before interpolation.

### No Content Security Policy (CSP)

- **Risk:** `index.html` has no CSP `<meta>` tag or HTTP header. If an XSS vulnerability were present, an attacker could execute arbitrary scripts, make network requests, or load malicious resources without restriction.
- **Files:** `index.html`
- **Current mitigation:** No user-supplied content is rendered. External image URLs are present but images cannot execute scripts.
- **Recommendations:** Add a CSP `<meta>` tag restricting script sources (`'self'`) and image sources (`'self' https://covers.openlibrary.org https://images.unsplash.com`).

### External Image URLs Loaded Without Validation

- **Risk:** Book image URLs point to `covers.openlibrary.org` and `images.unsplash.com`. While these are legitimate CDNs, there is no validation that the loaded content is actually an image. A compromised CDN could serve malicious content (though images alone are generally safe, SVG files can contain scripts).
- **Files:** `script.js` (lines 30–47)
- **Current mitigation:** The URLs are hardcoded and manually vetted. OpenLibrary and Unsplash are reputable services.
- **Recommendations:** Add `onerror` handlers on `<img>` elements to replace with a local fallback image. Validate that URLs serve expected image MIME types if dynamic loading is added.

## Performance Bottlenecks

### No Debouncing on Search Input

- **Problem:** The `input` event listener on the search bar fires the filter + re-render on **every single keystroke**. For 18 items this is negligible, but the pattern is costly — each keystroke triggers a full `.filter()` iteration, a `.map()` to rebuild HTML strings, and a full `innerHTML` DOM replacement.
- **Files:** `script.js` (lines 90–101)
- **Cause:** Direct event binding without debounce/throttle.
- **Improvement path:** Wrap the event handler with a `debounce` utility (e.g., 200ms delay) to avoid processing every keystroke. Alternatively, use a simple `setTimeout`/`clearTimeout` pattern.

### Full DOM Replacement on Every Search

- **Problem:** `innerHTML` destroys and recreates all DOM nodes on every search, discarding any internal browser state, image load progress, and CSS transitions.
- **Files:** `script.js` (line 83)
- **Cause:** Using `innerHTML` instead of a targeted DOM update or virtual-DOM approach.
- **Improvement path:** For the current scale (18 cards), minimal impact. For future scaling, consider:
  - Building DOM elements once and showing/hiding with CSS `display: none`.
  - Using a lightweight reactive approach.
  - At minimum, only update if the filtered result actually changed.

### No Image Lazy Loading

- **Problem:** All 18 book cover images start loading on page load, including those below the fold. Each image makes an HTTP request to external CDNs.
- **Files:** `script.js` (line 69), `index.html`
- **Cause:** No `loading="lazy"` attribute on `<img>` tags.
- **Improvement path:** Add `loading="lazy"` to all `<img>` elements to defer off-screen image loading.

## Fragile Areas

### Hardcoded Book Data

- **Files:** `script.js` (lines 29–49)
- **Why fragile:** All 18 book entries are hardcoded as a JavaScript array literal. Any change — adding a book, updating a price, fixing a typo — requires editing the source code. There is no data layer, API integration, or external data file.
- **Safe modification:** Edit the array directly in `script.js`. Ensure valid JSON structure and correct image paths.
- **Test coverage:** No tests exist to validate data integrity (e.g., no duplicate IDs, no missing required fields).

### External Image URL Dependencies

- **Files:** `script.js` (lines 30, 31, 32, 37, 38, 39, 41, 42, 43, 44, 45, 46)
- **Why fragile:** 12 of 18 books depend on third-party CDNs (OpenLibrary, Unsplash). These URLs could break if ISBNs are delisted, CDNs change their URL scheme, or services shut down. OpenLibrary covers API serves JPEG images at specific ISBN URLs that may not be permanent.
- **Safe modification:** Replace external URLs with local images in `images/`. Add `onerror` handlers to degrade gracefully.
- **Test coverage:** None — no visual regression tests to detect broken images.

### No Automated Tests

- **Files:** Entire codebase
- **Why fragile:** There are zero tests — no unit tests for the filter logic, no integration tests for search + render, no visual regression tests. Any code change risks breaking the search or display functionality without detection.
- **Safe modification:** Manual testing only — change code, reload browser, visually verify.
- **Test coverage:** 0%. Every function (`displayBooks`, filter callback, event listener) is untested.

## Scaling Limits

### Client-Side Rendering Limits

- **Current capacity:** 18 hardcoded book objects rendered client-side.
- **Limit:** While the current approach can handle hundreds of items with acceptable performance, at thousands of books the lack of virtualization, pagination, and debouncing will cause noticeable UI jank on each keystroke. The `innerHTML` full-rebuild approach has O(n) cost per render.
- **Scaling path:** Add pagination (e.g., 20 items per page), virtual scrolling, or server-side search with API integration.

### No Backend or Data Persistence

- **Current capacity:** All data exists in a flat file (`script.js`). No server, no API, no database.
- **Limit:** Cannot support user accounts, book purchases, reviews, or any dynamic data. The app is fundamentally a static page.
- **Scaling path:** Introduce a backend service (Node.js + Express or similar) with a database, and expose a REST/GraphQL API for the frontend.

## Dependencies at Risk

### OpenLibrary Covers API

- **Risk:** 7 books depend on `https://covers.openlibrary.org/b/isbn/...` URLs. OpenLibrary is a volunteer-run service with no SLA. URLs can change if ISBNs are reassigned or the service restructures.
- **Impact:** 7 books lose their cover images.
- **Migration plan:** Download cover images locally to the `images/` directory and reference them as local paths, eliminating external dependency.

### Unsplash Images

- **Risk:** 2 books depend on `https://images.unsplash.com/` URLs. Unsplash may change their CDN URL format or require API keys in the future.
- **Impact:** 2 books lose their cover images.
- **Migration plan:** Same as above — download and serve locally.

## Missing Critical Features

### No "No Results" Empty State

- **Problem:** When search returns zero matches, the user sees a completely blank grid with no message, no illustration, and no instruction.
- **Blocks:** Users cannot distinguish between "search returned nothing" and "app is broken."
- **Fix:** Add an empty state check in `displayBooks()` — if `booksArray.length === 0`, render a "No books found" message with a suggestion to try a different search term.

### No Cross-Field Search

- **Problem:** Search only matches `book.name`. Users cannot search by author, category, or price.
- **Blocks:** Findability — a user looking for "Productivity" books or books by "Robert Greene" gets zero results.
- **Fix:** Expand the filter to check multiple fields: `book.name`, `book.author`, `book.category`, and optionally `book.price`.

### No Debouncing on Search

- **Problem:** Every keystroke triggers a full filter-and-render cycle.
- **Blocks:** Performance at scale, wasted computation even at small scale.
- **Fix:** Implement a 200ms debounce on the `input` event handler.
